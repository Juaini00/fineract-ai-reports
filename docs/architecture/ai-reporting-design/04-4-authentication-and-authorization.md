# AI Reporting Service Design: 4. Authentication And Authorization

Source: `docs-old/ai-reporting-design.md`

## 4. Authentication And Authorization

The first authentication mechanism will use application-managed API keys.

Chat/reporting requests must include an API key:

```http
X-API-Key: <api_key>
```

`Authorization: Bearer <access_token>` is reserved for dashboard user authentication and API-key management. It is not accepted as an API key for AI assistant/chat routes.

The API key identifies the caller and determines which data and capabilities the caller can access.

### 4.1 API Key Principles

1. API keys are generated by this service.
2. Raw API keys are shown only once at creation time.
3. Only hashed API keys are stored in the database.
4. API keys can be revoked.
5. API keys can expire.
6. API keys can be scoped to capabilities, offices, products, and PII visibility.
7. Every request must be audited with the API key id, not the raw key.
8. API key validation happens before request understanding and AI planning.

### 4.2 API Key Generation Flow

```text
Admin / Developer
  -> POST /auth/api-keys
  -> service generates secure random key
  -> service hashes key
  -> service stores metadata and hash
  -> service returns raw key once
```

Example request:

```json
{
  "name": "local-dev-client",
  "expires_at": null,
  "allowed_office_ids": [1, 2, 3],
  "allowed_capabilities": [
    "savings_deposit_total",
    "savings_deposit_top_n"
  ],
  "can_view_pii": true
}
```

Example response:

```json
{
  "success": true,
  "data": {
    "id": "key_01hxyz",
    "api_key": "air_live_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx",
    "message": "Store this API key securely. It will not be shown again."
  },
  "error": null
}
```

### 4.3 API Key Runtime Validation Flow

```text
Incoming request
  -> extract API key from X-API-Key
  -> hash presented key
  -> find active key by hash
  -> check revoked_at is null
  -> check expires_at is valid
  -> load key scopes
  -> create ClientContext
  -> continue request
```

Client context example:

```json
{
  "api_key_id": "key_01hxyz",
  "owner": "Antun",
  "allowed_office_ids": [1, 2, 3],
  "allowed_capabilities": [
    "savings_deposit_total",
    "savings_deposit_top_n"
  ],
  "can_view_pii": true
}
```

### 4.4 Authorization Guards

After planning, the policy layer must verify:

1. The selected capability is allowed for the API key.
2. Requested office filters are within `allowed_office_ids`.
3. PII fields are masked when `can_view_pii = false`.
4. Query parameters cannot bypass API key scopes.
5. Async job results can only be read by the same API key or an admin key.

If authorization fails, the response must be explicit:

```json
{
  "success": false,
  "data": null,
  "error": {
    "code": "forbidden",
    "message": "This API key is not allowed to run the selected capability."
  }
}
```

### 4.5 API Key Endpoints

Initial authentication endpoints:

```text
POST   /auth/api-keys
GET    /auth/api-keys
GET    /auth/api-keys/{id}
DELETE /auth/api-keys/{id}
POST   /auth/api-keys/{id}/revoke
```

API key creation is protected by an authenticated admin user access token:

```http
Authorization: Bearer <access_token>
```

### 4.6 API Key Storage

The application database should store API keys in a table similar to:

```text
api_keys
  id
  name
  owner
  key_prefix
  key_hash
  allowed_office_ids
  allowed_capabilities
  can_view_pii
  expires_at
  revoked_at
  created_at
  last_used_at
```

The raw key must never be stored.

Recommended key format:

```text
air_live_<random_secret>
air_test_<random_secret>
```

The `key_prefix` can be stored for display/debugging, for example:

```text
air_live_abcd...
```

### 4.7 Auth Position In Runtime

Authentication happens before all AI-related work:

```text
Client request
  -> API key middleware
  -> ClientContext
  -> local classifier
  -> planner
  -> policy guard
  -> executor
```

This prevents spending tokens or executing expensive logic for unauthorized callers.
