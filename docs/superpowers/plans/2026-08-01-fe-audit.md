## TWO DIFFERENT AUDIT CONCEPTS — do not conflate them

These endpoints look similar and are not the same thing.

**1. Management audit trail** — the compliance record.
```
GET /management/audit                    (AuthenticatedManagementAdmin)
GET /management/audit/jobs/{job_id}      (same, job_id forced)
```
Returns cursor-paginated `SafeAuditEvent`s. Every field is allowlisted by the
backend — there is deliberately no arbitrary JSON field.

**2. Job event log** — the technical SSE replay.
```
GET /chat/jobs/{job_id}/audit            (AuthenticatedChatClient, not management admin)
```
Returns `ChatJobAuditTimeline { job_id, events }` — rows from `chat_job_events`,
which is the same log the SSE stream replays (status/stage/delta/final/error).

**This plan builds concept 1 only.** Concept 2 is technical debugging data and is
already visible live through the chat stream; mixing it into a compliance view
would blur what the record actually attests to. If you want it later, it is its
own page.

## Backend contract (read from source)

`GET /management/audit` query params — `from` and `to` are REQUIRED:
```
from       ISO8601   required
to         ISO8601   required
event_type enum      optional
outcome    enum      optional
job_id     uuid      optional
session_id uuid      optional
cursor     opaque    optional
limit      1..MAX    optional
```
An invalid cursor returns HTTP 400 with error code `invalid_cursor` — handle it
by resetting pagination, not by showing a generic failure.

Each event:
```jsonc
{
  "aggregate_type": "chat_job" | "chat_session" | "management",
  "aggregate_id": "<uuid>",
  "event_type": "chat.job_created" | "knowledge.retrieval_completed"
              | "context.assembled" | "policy.evaluated" | ...,
  "outcome": "...",
  "summary": { "kind": "...", ... },        // ← discriminated union, see below
  "sanitized_error": { "code": "..." } | null
}
```

### `summary` is a 9-variant discriminated union on `kind`

This is the central rendering fact. Six variants carry NO payload; three do:

| `kind` | payload |
|---|---|
| `job_created`, `job_completed`, `job_failed` | none |
| `clarification_requested`, `clarification_received` | none |
| `session_archived` | none |
| `policy_evaluated` | `capability_id`, `result`: `allowed` \| `denied` |
| `execution` | `query_id`, `row_count` (nullable) |
| `business_date_fallback` | `resolved_date` |

Render each variant on its own terms. A generic key-value dump would print
`[object Object]` for the payload-bearing ones and read as noise for the rest.

**An unrecognised `kind` must degrade gracefully** — show the raw kind string as
a label and no payload. New variants will be added backend-side over time, and a
compliance view that crashes or silently hides unknown events is worse than one
that says "unknown event type".

### `sanitized_error.code` is a closed enum, not a message

```
database_unavailable | dispatcher_unavailable | serialization_failed
provider_unavailable | provider_timeout | provider_malformed | unknown
```
Map each to human text in the UI. Do not print the raw snake_case code as if it
were a sentence. An unmapped code must fall back to something honest, not blank.

**Note the backend has already sanitised everything.** `SafeIdentifier` is
constrained to 1-128 ASCII alphanumerics plus `_-.`, errors are enum codes, and
there is no free-text field anywhere in the payload. So the FE's job here is
*rendering*, not sanitising — but do not therefore relax the no-raw-HTML rule.
